9  Doctrine: Principles, Decision Guides, and Named Anti-Patterns

This document compresses the whole research folder into what you would actually use in a design session: nineteen principles stated as prose, five decision guides stated as questions, and a catalog of named anti-patterns with their failure narratives. Nothing here is new; everything is justified in the earlier documents.

A register note before the principles: everything in this document is doctrine — deliberately imperative defaults distilled from documented S7 behavior and observed ecosystem practice, but laws of neither. The imperative mood is a choice: a crisp default you can overrule for stated reasons is more useful in a design session than a hedge you can ignore. “Always” and “never” here mean “strong default,” and when a principle collides with a real constraint, the earlier documents carry the reasoning needed to make the trade explicitly.

9.1 Principles

1. Model meaning before structure. Begin with the domain’s semantic atoms — the indivisible meanings and their laws — and only then compose the document structures that arrange them. Structure is the volatile part; meaning is the stable contract. Systems (and dialects of a domain) that share semantics can differ in structure and still interoperate; systems that share only structure are totally coupled.

2. Let construction be the proof. Arrange the system so that no unlawful object of a class can exist: boundary functions parse loose input into objects or fail loudly, validators run on construction and every replacement, and possession of the object certifies its laws. Downstream code demands classes instead of re-checking contents.

3. Constructors normalize; validators verify; boundaries translate. Coercion, canonicalization, and version gating happen once, at the boundary. Validators judge canonical values only, and stay pure and cheap because they run on every property write. A validator accommodating multiple input shapes is a parser in the wrong place, running forever.

4. Every invariant has one authoritative home. Place each law on its rung: external conformance at the wire, parsing at the boundary, type on the property class, local law in the property validator, cross-property law in the class validator, cross-object law in the aggregate root, operation legality in the mutator, developer invariants in assertions. Each rung assumes the rungs below and duplicates none. A cheap duplicate deliberately retained for better boundary diagnostics is a documented trade; a law found on two rungs by accident is a bug waiting to be two different laws.

5. Invariants live at the lowest point that sees everything they mention. A channel range belongs to the channel property; a start-before-end rule to the class; unique-ids-across-the-collection to the root that holds the collection. Placing a law lower than its visibility horizon makes it uncheckable; higher, and it runs too often and knows too much.

6. Presence is a four-way decision. Required-at-construction, nullable in the model, defaulted, and omitted-on-serialization are independent axes, and JSON’s omitted / null / empty forms are distinct meanings. Decide per property, record the policy, and never let one optional flag conflate what “the user cleared this” and “the user never touched this.”

7. Constants are identity, not state. If two instances of a class can never differ on a field, the field is part of what the class is: model it as a computed property or inject it at serialization, and keep it out of the constructor. Store it only when round-trip fidelity or spec evolution demands that instances carry it.

8. Represent alternatives as alternatives. Flag fields, mutually exclusive nullables, and mode strings are sum types flattened into products. Give variants honest representation: subclass families when fields or behavior differ, enum properties when only the tag differs, unions for primitive alternatives in one slot. Recover exhaustiveness with loud defaults and registry-driven tests.

9. Inherit for dispatch and substitutability; compose for structure. Parents contribute a property schema and a dispatch position to things that genuinely are the parent. Everything else — nesting, reuse, independent dimensions — is composition. Hierarchies stay shallow: abstract root, concrete leaves, intermediate levels only when they add both schema and a dispatch target. Inherit from a base type only when the object is that primitive.

10. Behavior belongs to generics, and interfaces are generic-sets plus laws. Design the verb vocabulary as deliberately as the class graph. An extension point is a set of generics an implementor must support and the laws those methods must satisfy — write the laws down, executably where possible. Reach for multiple dispatch when behavior genuinely varies along two type axes; it turns a conditionals matrix into small methods.

11. Values in the core, references in the shell. Records of fact are immutable S7 values transformed by pure functions; ongoing processes with identity — sessions, caches, conversations — are R6 or environments at the system’s rim. The domain must be reconstructible from the values alone.

12. Mutate atomically, through the front door. Invariants spanning several properties imply every update of those properties goes through one atomic replacement (S7::set_props()), wrapped in a mutator function so callers cannot do it wrong. Guarantees hold for clients of the exported surface; make the front door the easiest path.

13. One canonical artifact, many projections. When several outputs encode the same knowledge — an expression and a legend; a class graph and its documentation; a wire format and a pretty printer — designate one canonical source (usually a small, reviewable data structure) and generate every projection. Hand-maintained parallel encodings will diverge.

14. Property access is cheap and pure. Getters compute derivations; they never perform I/O, never mutate, never surprise. The moment x@thing can be slow or effectful, the object stops being data in the reader’s mind, and the whole value-semantics reasoning collapses.

15. Abstractions must earn their keep. Every layer of indirection pays rent by absorbing a demonstrated axis of variation — behavioral variation across types, meaning shared across sites, representation churn at a boundary. Abstract after the third occurrence, not the first. Delete layers that no longer pay. The ecosystem’s convergent evolution (independent projects growing the same enum/scalar/presence property helpers) is the positive form of this evidence: those particular abstractions keep earning.

16. Schemas are contracts and inputs, not blueprints. Validate against external schemas with the schema ecosystem’s own tools at the wire; read schemas as a census that informs hand-designed models; generate tables (enums, name maps, requiredness) rather than class graphs. A 1:1 mirror of an external type system imports its structure and discards the chance to encode meaning. And when your own model is the source of truth, store its constraints as data so the schema can be projected from it — one datum, and the validator and the published contract cannot disagree.

17. Refuse to guess. Where no correct behavior is known, an error beats a default. sqlr states the reason perfectly in declining to ship an “ANSI SQL” fallback dialect: an untestable default “would quietly accumulate behaviour no database had ever accepted.” The same logic condemns silent coercion of ambiguous input, fallback branches for “unknown type,” and any code path no test can exercise against a real authority. A loud, early error is information; a guess is deferred corruption.

18. Check as early as the inputs allow, as late as the context requires. The value of a check is proportional to the cost of the work it gates. Declarations should validate themselves at package load (a default violating its own bounds is the author’s bug, catchable before any user exists); configurations should validate fully before the expensive run they configure; and laws that mention context not yet in hand — data dimensions, live resources — should be declared at construction and checked in one named pass at the moment the context arrives, never guessed at and never skipped.

19. Failure travels one of two channels; choose per boundary. Conditions (classed, chained, cli-formatted) are the channel for bugs and contract violations — control flow that should stop. Result-style values are the channel when failure is an expected outcome the caller branches on as data — partial batches, fallible lookups feeding pipelines. Convert between the channels at one designed adapter (resultr’s wrap_in_result() is the model), never with ad hoc tryCatch scattered through the core.

9.2 Decision guides

Formulated as the questions to ask, in order, rather than flowcharts to follow mechanically.

Which object system? Is it fundamentally a homogeneous vector that must slice and live in data frames? — vctrs. Does it have identity and a lifetime, with observers sharing its changes? — R6 or an environment. Is it a domain value with laws and dispatchable behavior? — S7. Is it a veneer for ecosystem politeness? — S3. Mixed answers mean a hybrid, which is normal.

Which sum-type encoding? Do variants differ in fields, or does behavior dispatch on them? — subclass family under an abstract parent. Do they differ only in the tag? — enum-valued property. Is it several primitive shapes lawful in one slot? — union. Is the wire genuinely one bag with conditional fields, variants are many and trivial, and dispatch is never needed? — a discriminator plus class validator, chosen consciously as denormalization.

Which semantic-type tier? Does the concept merely repeat a validation shape across sites? — a reused property definition. Must it be impossible to confuse with its base primitive, or does dispatch need it, while it remains truly a primitive? — a class inheriting the base type. Does it have parts, or operations of its own? — a composite class.

Stored field, identity, or boundary-normalized? Can two instances of the class differ on it? If no — identity (computed property or serializer-injected). If yes — must round-trips preserve the caller’s exact value? If yes — stored, with lenient parsing at the boundary and one canonical stored form. Might the spec extend the value set? — stored enum with a parse-time version gate.

How deep should an embedded language go? Does anything analyze or transform the expressions, or target more than one output format? If no — opaque passthrough, with the engine’s validator as judge. Do humans hand-write the expressions painfully? — constructor combinators (shallow embedding). Is analysis, optimization, or multi-target translation the product? — typed AST with generic passes (deep embedding). Representation as deep as the analysis, and no deeper.

9.3 Anti-pattern catalog

Named, so design reviews can point at them.

Schema cosplay. Mirroring an external type system one class per interface. The model inherits every serialization quirk as a nominal type, class count tracks the schema forever, and no semantic layer exists because the schema never had one. Tell: classes whose names and nesting match the wire exactly, none of which ever gains a method.

Validator soup. The same law encoded in the constructor, the property validator, the class validator, and a boundary schema. The encodings drift; error messages disagree; nobody knows which one fired. Tell: fixing one validation bug requires a grep.

Shotgun parsing. Input checks interleaved with processing across many functions, no single point after which input is known-good, rejection possible after side effects. Tell: is.null() and is.character() guards deep in core logic; functions that “defensively” re-check their own package’s objects.

Boolean blindness. Check functions returning TRUE/FALSE whose callers immediately need the why or the what — so they re-derive it. Tell: if (is_valid(x)) { ... } followed by code that re-inspects x for the very facts validity established. Return parsed evidence, not verdicts.

The God validator. One class validator enforcing property-local rules, cross-property rules, and collection rules in a hundred lines. Placement discipline lost; every rung’s law in one place, none assumable by the others. Tell: a class validator that re-checks types.

Convert-everything. Routing lossy, contextual, one-to-many translation through a coercion generic because it exists. Coercion generics (convert(from, to)) suit faithful pairwise conversion; translation with diagnostics, options, and asset generation deserves named functions with room for a context argument and a report. Tell: a convert method with side effects or a dozen options.

Expression-system envy. Re-implementing an engine’s expression type system in property validators — badly, partially, and forever chasing the spec. The engine’s validator owns rung 0. Tell: a validator that walks nested lists interpreting operator names.

Decorative hierarchy. Inheritance introduced to share field names or to “organize” classes that never dispatch differently. Dispatch will eventually take the fake is-a seriously. Tell: an abstract parent with one child, or parents whose children never appear in a method signature.

The mutable domain object. Domain facts held in R6 “for convenience,” surrendering local reasoning, cheap snapshots, and testability to avoid reassignment. Tell: $clone() calls sprinkled defensively; tests full of setup/teardown for what should be a value.

Nullable confusion. NULL doing triple duty as “required but not yet supplied,” “explicitly cleared,” and “omitted on the wire,” with no presence policy. Tell: code that cannot distinguish an untouched field from a cleared one; serializers with ad-hoc per-field if (!is.null()) decisions.

Premature DSL. Combinators, quotation, and clever printing built before any user wrote the target structures by hand long enough to reveal which constructions are actually painful. The DSL then ossifies the wrong abstractions. Tell: a DSL whose vocabulary mirrors the wire format one-to-one instead of the domain’s own idioms.

Effectful getter. A property that reads a file, calls an API, or mutates a cache. Data access becomes action at a distance; cost and effects become invisible at every @. Tell: property access inside a loop dominating a profile; getters needing error handling.

Boundary leakage. Wire names, omit-empty decisions, or dialect quirks appearing in core logic instead of the one serializer pair. Tell: "source-layer" (the wire spelling) as a string anywhere except to_wire()/from_wire().

9.4 A closing note on judgment

The principles compress experience, but they trade against each other in real designs: parse-don’t-validate argues for strictness at the boundary while round-trip fidelity argues for permissive pass-through nodes; earned abstraction argues for waiting while semantic atoms argue for naming meanings early; shallow hierarchies argue against intermediate classes while shared schema sometimes argues for them. The earlier documents exist so that when two principles collide, the reasons behind each are available and the trade can be made explicitly, on the record, instead of by whichever slogan was remembered first.
