8  Ecosystem Field Guide: What Real S7 Packages Teach

Each package below was verified against its current documentation or source (September 2026). The interest is not in their domains but in the design moves they demonstrate — each is the clearest available exhibit for at least one pattern from the preceding documents. The guide is organized into five thematic clusters, with cross-cutting observations at the end.

8.1 Cluster A — Values, state, and architecture

8.1.1 ellmer — the hybrid architecture, and dispatch as a plugin system

ellmer (tidyverse; LLM chat from R) is the reference example for mixing object systems by semantics rather than ideology. The Chat object is R6, and the documentation is explicit about why: a conversation is mutable state with identity — you send messages to it, it accumulates turns, it runs the tool-invocation loop — and value semantics would force callers to reassign after every exchange. Branching a conversation requires an explicit $clone(), exactly the ceremony value semantics would have made free, and ellmer accepts that trade consciously.

Everything flowing through the Chat is S7 values: Turn (with UserTurn, SystemTurn, AssistantTurn subclasses — a sum type as a subclass family, where the assistant variant carries extra fields like tokens, cost, and finish reason), Content objects inside turns (text, images, tool requests, tool results — another variant family), Model (a small immutable configuration value), and Provider. Records of fact are values; the ongoing process is a reference.

The Provider hierarchy doubles as the package’s plugin system: the README lists ten official and nine community providers, and supporting a new LLM service means subclassing Provider and registering methods on the existing generic vocabulary for request building and response parsing. The data axis of the expression problem, held open on purpose — community providers extend ellmer without touching its core.

8.1.2 ragnar — honest base-type inheritance and the enriched table

ragnar (tidyverse; retrieval-augmented generation) contributes two small, perfect exhibits.

MarkdownDocument is an S7 class inheriting from character: a document is a length-one markdown string, with an @origin property riding along. The inheritance passes the honesty test of 05-composition-and-dispatch.qmd — treating the object as text is semantically sound, not merely convenient. Its constructor is a boundary parser in miniature: it normalizes (collapses lines, enforces UTF-8) so that, quoting the docs, “downstream code can rely on a consistent format” — parse-don’t-validate stated as user documentation.

MarkdownDocumentChunks inherits from tibble: chunk data is genuinely tabular (start, end, context columns; users will filter and mutate it), so it should be a data frame — but it carries the source document as a @document property, keeping the provenance attached to the value rather than in a parallel variable the user must not lose. An enriched table: structural behavior from the base class, domain identity and payload from S7.

8.1.3 tooey — the Elm architecture as a whole-program design

tooey (devOpifex) is a terminal UI framework built on the Model–View–Update architecture (The Elm Architecture): an application is three pure functions — init(model) producing initial commands, update(model, msg) mapping a state and a message to a new state plus commands, and view(model, buf) rendering state into a screen buffer — while a runtime loop owns the terminal, the clock, and input events, feeding them in as messages (is_key, is_tick) and executing returned commands (cmd_tick, cmd_quit).

This is the functional core / imperative shell of 02-values-and-state.qmd in its most disciplined published form: all state transitions are pure data-to-data functions, all effects are values (commands) interpreted by the shell, and the framework — not convention — enforces the boundary. Even in a domain as imperative-seeming as a live terminal UI, mutation is confined to a runtime the application author never touches. It is also a working answer to “where do messages and events fit in a value-oriented design”: as plain data dispatched over, exactly like any other variant family.

8.2 Cluster B — Documents, schemas, and serialization

8.2.1 stacbuildr — the document-object-model pattern, complete

stacbuildr (STAC geospatial catalogs) is the fullest single exhibit of 06-documents-schemas-dsls.qmd: STAC 1.1.0 Catalogs, Collections, and Items as an S7 class graph, serialized to STAC JSON, validated against the published JSON schemas (rung 0 delegated to the specification’s own authority), with extensions (electro-optical, raster, projection, and more) layered onto the core following the spec’s own shared bands model.

Two moves stand out beyond the basics. First, the boundary-constructor family: item_from_terra(), item_from_sf(), item_from_lidr() lift native geospatial objects — rasters, geometries, point clouds users already hold — into document nodes, extracting extents, projections, and band metadata at the boundary. Second, the document as data: a Collection supports length(), [[, as.data.frame() (one row per item, properties as columns, list-columns for structured values), and sf::st_as_sf() — the object graph projects into the tabular and spatial idioms R users already know, rather than forcing graph navigation. Its write_stac() also encodes the STAC best-practices catalog layouts (self-contained, relative, absolute) as an explicit enum that maps one-to-one onto PySTAC’s CatalogType — cross-ecosystem vocabulary alignment as API design.

8.2.2 S7schema — schema as boundary contract, productized

S7schema (Novo Nordisk; CRAN) is the schema-as-boundary-contract posture as a reusable framework: YAML configuration files validated against JSON Schema definitions using AJV (via V8), with the resulting configuration objects inheriting from both S7 classes and base lists — full conformance checking delegated to the schema ecosystem’s standard tooling, R-side typing layered on for downstream extension through custom classes and methods. Notably it does not re-derive the schema’s rules as property validators — the two layers check different things.

8.2.3 rapid — an external specification as a strict domain object

rapid (api2r) converts OpenAPI descriptions into R objects of a new S7 class that, in its own words, “enforces a strict, opinionated schema.” The design posture is instructive: rather than wrapping the OpenAPI JSON loosely, it parses the specification into a validated domain object intended as the substrate for downstream code generation (the beekeeper and mockplumber packages). An API description is exactly the kind of declarative document 06 describes, and rapid is the front-end that makes it lawful before generators consume it — parse once at the boundary, generate from the certified object.

8.2.4 sqlr and its dialects — schema as the middle term, round-trip as oracle

nbenn/sqlr has matured into one of the most architecturally articulate S7 packages anywhere, and its README states its thesis in one sentence: what R lacked was “a representation of a schema that is neither a string nor a connection, which you can build, render, reflect and compare.” That middle term — the schema as a first-class value between the DDL text and the live database — is the document-object-model argument made for SQL.

Four design moves reward study. Dialects are objects, not connections: rendering (sqlr_render(schema, sqlite())) needs no server, no driver, and the core package renders nothing on its own — dialect packages (sqlr.postgres, sqlr.sqlite) supply the spellings via multiple dispatch (render_sql(x, con) dispatching on object and dialect at once). There is deliberately no generic fallback: nothing renders “ANSI SQL,” because no engine implements it faithfully and “an untestable default would quietly accumulate behaviour no database had ever accepted” — an unregistered dialect is an error rather than a guess. Reflection closes the loop: sqlr_reflect(con) reads a live database’s catalog back into the same representation sqlr_render() consumes, and the round trip (sqlr_equal(schema, sqlr_reflect(con))) is, in the package’s own words, “the package’s own test oracle.” Equality is structural and semantic: constraints and indexes are matched on what they constrain, not their order or auto-generated names, so a hand-written schema compares equal to a reflected one — and sqlr_diff() reports meaningful differences, the explicit groundwork for a future migration generator. Rendering even performs real compilation work: tables emit in dependency order and cycle-closing foreign keys are lifted into trailing ALTER TABLE statements.

8.2.5 typedjson — round-trip fidelity as the entire product

typedjson (same author) makes the round-trip law of 06 into a package: it “writes an R value as JSON a human can read, and reads it back unchanged.” Its README diagnoses the existing landscape precisely — jsonlite is readable but lossy (doubles return as integers, all-NA vectors lose their type, empty typed vectors collapse to list()), serializeJSON is faithful but unreadable — and stakes out the missing quadrant: ordinary JSON for ordinary values, with annotations only for what JSON cannot express (integer versus double, typed missing values, non-finite doubles, attributes, language objects, and S3/S4/S7 objects). That principle — annotate the minimum needed to make the round trip an identity — is the presence-policy and wire-universe discussion of 03-types-and-meaning.qmd turned into a serialization format.

8.2.6 structr — the contrast case: a compiled schema, not an object system

structr (ixpantia) is deliberately not S7 — it is Rust (serde, simd_json) behind an R schema DSL (s_map(), s_integer(), s_optional(), build_structure()) — and it earns its place here as the boundary of the boundary. structr compiles a schema once and then parses and serializes against it, strictly: type mismatches, missing fields, and unexpected nulls are errors. It is rungs 0–1 of the checking ladder as a standalone, high-performance tool, with no domain objects at all — the output is plain R lists that are known to conform. The lesson is about division of labor: when the need is pure wire conformance at speed, a compiled schema validator beats an object system, and an S7 domain layer is what you build on top of such a boundary when invariants, identity, and dispatch are needed beyond the parse. Its “all fields required unless s_optional()” default is also the right polarity for presence policy — opt into looseness, never out of it.

8.3 Cluster C — Errors, contracts, and introspection

8.3.1 resultr — errors as values, the Result/Option sum type

resultr implements Rust’s Result/Option vocabulary in S7, and its Result.R is a compact tour of the sum-type playbook: an abstract Result parent “used for the purposes of dispatch,” Success and Failure subclasses each carrying one property, and the full monadic combinator set as generics — unwrap(), unwrap_or_default(), unwrap_or_else(), and_then(), inspect(), expect() — with per-variant methods (the Failure method for and_then simply returns itself, which is railway-oriented short-circuiting).

Three details are worth stealing. First, the boundary between conditions and values is a generic: wrap_in_result() has methods for class_any (wrap in Success), class_error and class_warning (wrap in Failure), and Result itself (pass through) — so R’s condition system is converted into value-level errors at exactly one point, inside and_then()’s rlang::try_fetch(). Second, write-once properties: both @value and @error use a setter that errors if the slot is already set — a poor man’s immutability enforcement, making the certificate tamper-evident. Third, expect() dispatches on list(Success, class_character) — multiple dispatch pressed into service for argument typing. The broader lesson feeds 04-parse-dont-validate.qmd: R has two error channels, conditions (control flow) and values (data flow), and a design should choose per boundary which one crosses it.

8.3.2 s7contract — interfaces, traits, and executable laws

s7contract (CRAN) imports the Go-interface/Rust-trait worldview onto S7 dispatch, and its README now shows the full progression. Structural interfaces are named sets of required generics, checked by method availability (implements(Circle, Shape)), with missing_requirements() reporting exactly which verb is absent — Go’s implicit satisfaction, made queryable. Traits require explicit impl_trait() registration and support default methods and associated constants — Rust’s explicit opt-in. Progressive runtime checks let an interface requirement carry argument and return specifications, enforced in contract-scoped evaluation (with(Interface, expr)), so a method that returns the wrong type fails at the call with a typed message. Generative laws combine named generators, shrinking, and tinytest expectations (expect_law()), testing the behavioral half of the contract that no dispatch table can see. Its stated limits are as instructive as its features: all checks are runtime, and passing generated cases proves nothing universally — honest about what a dynamic language can and cannot recover of Rust’s compile-time story.

8.3.3 datarr (reflect) — the metaobject payoff of classes-as-values

datarr (package name reflect) builds runtime reflection for base R and S7: immutable descriptor objects for properties, methods, and callables, with explicit capability predicates. Its s7.R shows what S7’s classes-as-first-class-values design makes possible in ordinary R code: reflect_properties() walks class@properties and the constructor’s formals to report each property’s declared type, default presence, requiredness (a formal equal to the empty symbol), validator presence, and whether it is inherited (tracing the declaring class up the parent chain); reflect_methods() enumerates a generic’s method table and can attach S7’s own method_explain() dispatch trace; reflect_callable() distinguishes generics, methods, and closures with their signatures. The descriptors are themselves S7 objects — reflection modeled in the system being reflected.

Two further touches: reflect_validate() wraps S7::validate() with a chained, classed condition (the error-design discipline of 04 applied to the metalevel), and reflect_check_project() audits a package against declared conventions (export naming policy, dependency policy, lifecycle documentation) — conventions turned into executable checks, which is the same move as s7contract’s laws applied to project structure instead of object behavior.

8.4 Cluster D — Systems built on S7 at scale

8.4.1 rtemis — constraints as data, one declaration to rule four artifacts

rtemis (machine learning framework, 150+ stars) rewrote its entire supervised/unsupervised backend from R6 and S3 onto S7, and its 010_Props.R is the most sophisticated property foundation yet published. The core idea: every prop_* factory attaches a PropertySpec — a nested S7 object in which the property’s type, bounds, enum, default, nullability, and roughly twenty further axes are stored as data rather than closures. Because the constraints are data, one declaration mechanically produces four artifacts: the R validator, the default, a JSON Schema (via S7_to_JSONSchema()), and downstream a TUI configuration form. This is the “one canonical artifact, many projections” principle executed at the level of individual properties, and it is the reverse arrow of schema-driven development: the model generates the schema.

The spec’s axes are a checklist of presence-and-arity distinctions most designs never separate: container (none / array / map / matrix / table / struct / factor, each with a documented rationale — a factor serializes as {levels, codes} because a label array would lose level order and empty levels); broadcast (a scalar stands for the whole container) kept mutually exclusive with tunable (an array alongside a value is a search space, one nesting level above the value’s own type — the comment warns “a reader must never infer one from the other’s shape”); tune_on_null versus default_on_null (two different meanings of NULL, declared rather than guessed); constant (class identity) versus fixed-but-settable; applies_when (conditional applicability among sibling properties, encoded as data and checked centrally); and data_bound — validity constraints tied to training-data dimensions (n_features, n_cases, class names) that cannot be checked at construction and are instead resolved in one pass against the data before any training begins.

Around this foundation sit two more discipline exhibits. Factory-time validation: a PropertySpec’s validator checks that the declared default conforms to its own spec, so a bad declaration “fails at factory time — i.e. at package load — rather than at first instantiation.” Eager configuration validation: the user-facing setup_*() functions (setup_LightGBM(), setup_GridSearch()) construct validated configuration values before a run that may train thousands of models, so user error surfaces in milliseconds, not hours. There is even an authorship-policy annotation (agent_writable) deliberately excluded from published schemas because who may set a property can change while what the property is cannot — a crisp example of keeping volatile policy out of stable contracts.

8.4.2 quickr — S7 as a compiler’s intermediate representation

quickr (Tomasz Kalinowski; CRAN) compiles R functions to Fortran. Users annotate functions with an in-language type DSL — declare(type(x = double(NA))), a runtime no-op the compiler reads, expressing element modes, shapes, and size relationships between arguments (double(n) twice means “same length”) — and quick() lowers the R code through a typed intermediate representation to generated Fortran compiled via R CMD SHLIB. That IR is S7: typed values (e.g. a FortranSubroutine consumed as fsub@name, fsub@closure) flow between compiler stages. This is rung 3 of the AST escalation ladder, justified because analysis and translation are the product. The broader pattern — R syntax as source language, S7 objects as typed IR, a foreign language as target — recurs wherever multi-target analysis appears.

8.4.3 optimizers7 and parameters7 — extracting the private re-implementations

The statmodels7 family (optimizers7, parameters7, with distributions7, linkfunctions7, basis7 as siblings) is built on one sharp observation, stated in both READMEs: almost every modeling package privately re-implements the same mathematics — optimizers as while (!converged) loops with “a tolerance compared against whatever quantity the author had to hand,” constrained parameters as bespoke parametrizations (nlme’s pdMat, lme4’s theta, every mixture package’s softmax) — “none exposing a derivative, none reusable from outside.”

The response is semantic atoms at the level of mathematical behavior: an optimizer is an S7 object carrying its algorithm and settings, written once against one objective interface; a stopping rule is a separate, composable object — the observation that “the stopping rule, which decides what the whole procedure means by finished, is usually a number buried three levels down” is an indirection-rent argument of unusual clarity. A constrained parameter is “a fixed mathematical object: a map from an unconstrained vector onto the set where the parameter lives … with its inverse, its derivatives, and the quantities a likelihood asks of the value” — evaluated, inverted, differentiated to fourth order, as an object. Both packages are also deliberately narrow (“an optimizer here minimizes the function it is given, with no notion of an observation”) — boundary discipline about which layer is allowed to know what.

8.5 Cluster E — Foundations and utilities

8.5.1 s7x and the R-ArcGIS stack — convergent evolution of the foundation layer

s7x (Josiah Parry) is a utility layer over S7 providing an extensible Enum class (value + variants, validated, castable to character), scalar properties, range properties, and property unions and intersections. The R-ArcGIS packages (arcgisutils, arcgisviz) consume it at scale to model a very large TypeScript-shaped API surface. Together with rtemis’s PropertySpec factories and the private property-factory layers appearing in document-modeling codebases, this is now a three-way independent convergence on the same helper stratum — enum formalization, scalar/bounded factories, presence-aware wrappers — which is strong evidence about which foundation abstractions are genuinely load-bearing.

8.5.2 objectstore — interface-first design, embryonic

objectstore (Hugo Gruson) is an “Object Store Interface in R with S7” at a very early stage (a handful of commits). Its interest is the shape of the bet: defining the abstract interface to object storage as the package’s product, with backends to dispatch beneath it — the generic-vocabulary-as-plugin-contract pattern (ellmer’s Providers, sqlr’s dialects) applied to storage. One to watch rather than to study yet.

8.5.3 provider — the adjacent case

provider (healthcare provider APIs) is included for completeness as a data-domain API client in this orbit; its published surface is a tidyverse-style httr2 client rather than an S7 architecture. It illustrates the before state of the patterns in this guide — a domain of record types (providers, enrollments, claims) currently represented as tibbles, which is entirely reasonable, and exactly the kind of surface where semantic atoms and typed records would be the next step if invariants started to matter.

8.6 Cross-cutting observations

Reading the ecosystem as a whole rather than package by package:

Hybrids are the norm, not the exception. ellmer (R6 + S7), ragnar (S7 + tibble), S7schema (S7 + list + V8/AJV), sqlr (S7 generics + S4 DBI connections), structr (Rust boundary + plain R values), tooey (pure functional core + runtime shell). Mature designs choose per-object semantics and let the compatibility layer do its job.

Constraints-as-data keeps winning. rtemis stores property constraints in a spec object and generates validators, schemas, and forms from it; sqlr stores a schema as a value and generates DDL, comparisons, and diffs from it; rapid parses OpenAPI into a strict object that generators consume; structr compiles a schema once and parses against it. The common shape: represent the contract as inspectable data, derive every enforcement and projection mechanically, and never encode the same fact twice.

Round-trip as oracle recurs independently. sqlr’s render/reflect equality is “the package’s own test oracle”; typedjson’s entire product is the identity round trip; stacbuildr writes and reads catalogs through the same representation. When a package models a wire format, the round-trip law is the highest-value test it can own.

Errors have two channels, and good designs choose deliberately. Conditions (rlang/cli, chained, classed — datarr’s reflect_validate) for control-flow errors; values (resultr’s Result, converted from conditions at exactly one boundary) for data-flow errors. The anti-pattern is mixing them ad hoc.

Base-type inheritance appears exactly where it is honest. A markdown document is text (ragnar); an enum value is a string (s7x). Nobody publishes a subclassed primitive stuffed with structure.

Multiple dispatch is rare and decisive. sqlr’s render_sql(x, con) (object × dialect), resultr’s expect(Success, class_character), S7’s own convert(from, to). Everywhere it appears, the alternative was a conditionals matrix.

Rung 0 is always delegated. stacbuildr to the STAC schemas, S7schema to AJV, sqlr to the actual database engines (refusing even to pretend a generic dialect exists), structr to a compiled Rust validator. None re-implements an external specification internally.

The document-object-model shape recurs across unrelated domains. Catalogs, configurations, conversations, styles, SQL schemas, API descriptions, typed IRs, even terminal screens (tooey’s buffer): nested values, aggregate roots, boundary parsers, projection serializers. The domain changes; the anatomy does not.
